# 开发日志 (WORKLOG)

> 多轮对话生成系统 — 开发过程中的思考与决策记录
> 面向未来开发者（包括几个月后的自己）
> 最后更新：2026-08-06

本文件记录「为什么这么做」而非「做了什么」（做了什么见 [CHANGELOG.md](CHANGELOG.md)）。
每条记录包含：背景 / 问题 / 决策 / 理由 / 结果，便于追溯设计动机。

---

## 阶段一：基础复现（2026-04-27 ~ 2026-04-29）

### 2026-04-27 项目重构启动（"第二次开始"）

**背景**：原版催收对话生成代码是单文件硬编码脚本，所有业务参数写死在代码里，换一家公司就要改代码，无法复用。

**决策**：推倒重写为「配置驱动 + 模块化」架构。把所有硬编码常量（`MODULES`、`MAX_REPEAT`、`A_SET`、`B_SET`、`TERMINAL_NODES`、`INSERT_NODES`、`PRESSURE_PROB`）抽到 YAML。

**理由**：配置与代码分离后，切换公司只换配置文件，非开发人员也能调参。这是后续一切抽象的前提。

**结果**：奠定 `config.py` 作为统一配置入口的设计基调。

---

### 2026-04-28 祖先继承链与条件匹配

**问题**：话术模板用 `parent(继承)` 列表达父子关系，子行继承父行属性；条件匹配（`conditions(条件)`）规则粗放。

**决策**：
1. 实现 `get_ancestors` 沿 `parent` 列向上回溯，构建继承链。
2. 细化条件匹配规则实现，正确替换 `{变量}` 标签。

**踩坑**：占位符替换最初有缺失，话术中的 `{逾期天数}` 等变量没填进去 → 后续（0.2.0）专门修复。

**路径生成缓存**：同日加入路径缓存（`all_paths_{n}_{seed}.json`），避免重复生成相同配置的路径，大幅加速二次运行。

---

### 2026-04-29 强制不重复路径

**问题**：概率矩阵有限状态机下，路径组合数有上限，但早期生成经常出现大量重复路径，导致对话多样性不足。

**决策**：强制生成不重复路径——持续生成直到达到目标数量或最大尝试次数。

**理由**：宁可耗时也不产出重复，保证训练数据多样性。这是质量优先于速度的原则确立点。

---

## 阶段二：工程化重构（2026-05-27 ~ 2026-06-04）

### 2026-05-27 依赖注入：RandomService 与 Logger

**问题**：原代码用全局 `random`，无法控制种子，生成结果不可复现；测试时也无法固定随机序列。

**决策**：引入 `RandomService` 封装 `random.Random`（独立实例，非全局）+ `numpy` 种子同步，通过构造函数注入到所有需要随机的组件。Logger 同样改为依赖注入。

**理由**：
- 可复现性是数据合成工具的刚需（同种子同结果，便于 debug 与回归）。
- 独立实例避免多进程间随机状态污染。
- 依赖注入让单元测试可 mock 随机源。

**结果**：这一决策成为后续「断点续传可恢复」「多进程独立种子」的基础。

### 2026-05-27 断点续传

**问题**：生成数万条对话耗时长，中途崩溃要全部重来。

**决策**：检查点机制 `checkpoint.json` 只存 `next_index`，临时文件用追加模式（`mode="a"`），恢复时从 `next_index` 继续。

**结果**：生成完成后自动删除检查点，临时 JSON Lines 合并为标准 JSON 数组。

---

### 2026-06-03 data_loader 取消预过滤

**问题**：`load_sheets` 早期在加载时就按条件关键词预过滤行，导致条件逻辑耦合在数据层，无法支持动态条件（如「未逾期」需要运行时看 case 的逾期天数）。

**决策**：取消 `load_sheet` 的预过滤，保留所有行；条件筛选下沉到 `DialogueBuilder` 中由 `ConditionEvaluator` 动态执行。

**理由**：职责分离——数据层只管加载，业务层负责筛选。这是后续条件解析器可扩展的前提。

### 2026-06-03 随机金额防御保护

**问题**：金额字段含「元」字（如「5000元」），直接转数字报错。

**决策**：`parse_case_info` 自动提取数字部分，同时保留原始字符串。

**理由**：在系统边界（外部数据）做防御性解析，内部代码无需关心格式。

---

### 2026-06-04 重构 DialogueBuilder + DRY

**问题**：`dialogue_builder.py` 施压话术构建逻辑重复多处，难以维护。

**决策**：
1. 抽象私有方法构建对话，符合 DRY。
2. 增加 Trace 记录追溯话术来源。
3. 引入 pytest 单元测试。

**理由**：这是从「能跑」到「可维护」的关键转折。测试先行的意识在此建立。

### 2026-06-08 变量重命名 stop_prob → flexible_stop_prob

**决策**：将 `stop_prob` 改为 `flexible_stop_prob`。

**理由**：`stop_prob` 语义模糊（停止什么？），`flexible_stop_prob` 明确指向 `flexible_stop` 字段的终止概率。**清晰的命名本身就是文档**。

---

## 阶段三：工厂抽象与可扩展性（2026-06-11 ~ 2026-06-17）

### 2026-06-11 工厂模式全面铺开

**背景**：要支持不同业务线（小赢双目录案例、未来可能的其他加载方式），且时间/条件解析都需可扩展。

**决策**：所有可扩展组件抽象基类 + 工厂方法：
- `CaseLoader` (ABC) → `DefaultCaseLoader` / `XiaoyingCaseLoader`
- `ConditionEvaluator` (ABC) → `KeywordConditionEvaluator`
- `TimeGenerator` (ABC) → `SimpleNaturalTimeGenerator`
- 集中在 `factory.py` 的 `create_*` 方法按配置 type 分支创建。

**理由**：依赖倒置——高层 `DialogueBuilder` 依赖抽象而非具体实现；新增行为通过继承扩展，不修改既有代码（开闭原则）。

**结果**：后续新增 `OverdueConditionEvaluator`、`AbsolutePressureStrategy` 等都无需改动主流程。

### 2026-06-11 配置自动同步

**问题**：切换话术模板后，`modules` 和 `max_repeat` 经常忘记同步配置，导致运行报错或行为异常。

**决策**：`auto_sync_config_from_excel()` 在 `load_config` 后自动从 Excel 提取 `modules` 与 `max_repeat` 覆盖配置。

**理由**：让机器替人记住易错的事。配置仍是单一事实来源的兜底，但 Excel 自动同步减少人为疏漏。

---

### 2026-06-12 施压前移与策略工厂

**问题**：施压话术位置不可控，要么集中开头要么随机散布，不符合真实催收「前轻后重」的节奏。

**决策**：
1. 施压前移——动态概率模型让施压自然集中于对话中后段。
2. 抽象施压概率策略工厂 `create_pressure_strategy`。

**结果**：施压分布更贴近真实业务流程。

### 2026-06-17 动态概率双层解耦

**问题**：施压概率既要控制「位置归一化方式」（按路径长度 vs 按绝对索引），又要控制「概率曲线形状」（指数 vs Sigmoid）。早期两者耦合在一起，调一个影响另一个。

**决策**：拆成两层：
- `PressureStrategy`：只管计算归一化位置 `t`（0~1）。
- `ProbabilityCalculator`：只管把 `t` 映射成概率值。

**理由**：单一职责。位置策略和曲线形状是正交的两个维度，解耦后可任意组合配置。

## 阶段四：可观测与分析（2026-06-22 ~ 2026-06-24）

### 2026-06-22 施压覆盖率饼图

**决策**：分析报告增加施压覆盖率饼图。

**理由**：直方图看分布，饼图看覆盖率（有多少对话被施压了），两者互补。

### 2026-06-24 Trace + 分析报告集成

**问题**：对话生成是黑盒，无法回答「为什么这条对话在这里施压？为什么提前结束了？」。

**决策**：`TraceCollector` 记录每条对话的决策点（施压位置、再见触发、停止原因、模块轮次），生成后由 `DefaultAnalyzer` 自动产出可视化报告。

**理由**：数据合成工具必须可解释、可调优。Trace 是连接「配置参数」与「生成效果」的桥梁。numpy 类型递归转原生（`_convert_to_native`）确保 JSON 可序列化。

## 阶段五：配置化业务规则（2026-06-30 ~ 2026-07-06）

### 2026-06-30 B_set 概率 50% 转移到自身

**问题**：B 集模块间跳转过散，A 集模块回跳概率不合理。

**决策**：路径生成时，将 `b_set` 概率的 50% 转移到当前模块自身。

**理由**：让 B 集模块有合理的自循环倾向，更贴近真实对话中「同一话题反复纠缠」的模式。

### 2026-07-01 累加 A_set 概率

**决策**：累加 `a_set` 概率，确保 A 集只出现一个的规则生效。

**理由**：A 集是「问题原因」，一次对话只能有一个主因，需在路径层强制约束。

### 2026-07-06 CLI + 业务规则配置化

**问题**：硬编码的跳转规则散落代码，换业务线要改源码。

**决策**：
1. `main.py` 改用 `argparse`，`-c/--config` 指定配置文件。
2. `transition_rules` 配置化，支持 `allow_list`（白名单）/ `deny_list`（黑名单）两种模式。

**理由**：业务规则是最常变的部分，必须配置化。CLI 让批量任务脚本能传参，不再依赖改默认值。

### 2026-07-06 配置目录结构调整

**决策**：`configs` 结构调整，配置项按功能模块分组并加详细注释。

**理由**：配置文件本身是最好的文档——分组 + 注释让非开发人员也能读懂可调参数。`general_full_template.yaml` 即此原则的集大成。

### 2026-07-07 统一异常抛出

**决策**：统一异常抛出机制（部分模块开始落地）。

**理由**：早期各模块异常风格不一，排障困难。统一后错误信息更可定位。**注：截至 0.8.0 仍部分在推进中。**

## 阶段六：业务线适配（2026-07-13 ~ 2026-07-20）

### 2026-07-13 suning 项目占位信息

**决策**：为苏宁业务线添加占位信息。

**背景**：多业务线并行，需保证主架构不变下适配不同话术与案例结构。

### 2026-07-14 ~ 2026-07-15 未逾期条件解析重构

**问题**：苏宁项目需要支持「未逾期」场景，旧条件解析器只认「逾期」关键词，无法处理 `未逾期&{逾期天数}小于0` 这类复合表达式。

**决策**：
1. 新增 `OverdueConditionEvaluator`，支持新格式表达式。
2. 重构条件解析，职责分离——`evaluate()` 返回布尔，`evaluate_with_metadata()` 返回带元数据的字典。
3. 继承链条件解析迭代到 V3，正确处理当前行 + 后代链的继承判断。

**踩坑过程**（从提交记录可见 V1→V2→V3 多次迭代）：
- V1（正值）：先解决逾期天数为正值场景。
- V2：修正逻辑错误。
- V3：最终正确处理继承链的条件判断。

**教训**：复杂条件逻辑不要一次写完，分阶段验证（正值→零值→负值→继承链）。

### 2026-07-20 self_loop 循环

**决策**：新增 `self_loop_modules` 配置，让特定模块（如「语音留言」）按占比独立循环，不参与正常路径流转。

**理由**：有些模块（语音留言）在真实业务中是独立触发的，混在主路径里会破坏对话连贯性。

## 阶段七：数据后处理工具（2026-08-05 ~ 2026-08-06）

### 2026-08-05 case 分离工具

**问题**：苏宁未逾期场景需要把 `逾期天数=0` 的案例单独筛出来训练。

**决策**：`tools/filter_zero_overdue.py` 批量扫描 `.txt` 案例文件，按模式匹配筛选并复制到新目录。

**理由**：数据预处理工具与主生成流程解耦，独立工具更灵活、可单独运行。

### 2026-08-05 ~ 2026-08-06 相邻 assistant 去重

**问题**：生成数据中存在相邻 assistant 话术高度重复（同一句施压/告知连续出现），影响训练质量。

**决策**：`tools/deduplicate_assistant.py` 用 `SequenceMatcher` 计算相似度，按阈值删除相邻重复的 `user+assistant` 轮次，保留首次出现。

**迭代过程**（多日多次提交）：
1. 初版实现相邻去重。
2. 添加阈值筛选（支持 0~1 相似度，1.0 为完全相同）。
3. 简化保留逻辑——只保留首次出现。
4. 添加统计次数（重复对话数、删除轮对数）。
5. 统计测试验证效果。

**设计要点**：
- `ignore_numbers=True` 默认忽略数字，避免金额/日期占位符造成的「假重复」误判。
- `return_stats=True` 返回统计，便于评估数据质量。
- 配套 `find_adjacent_assistant_duplicates.py` 先检测导出，再用 `deduplicate_assistant.py` 清洗——**先观测后处理**的工作流。

**理由**：去重是数据质量最后一道防线，但必须可观测（统计影响范围）而非黑盒清洗。

## 跨阶段经验总结

### 1. 抽象时机
不要过早抽象。本项目的工厂模式是在「确实出现第二种实现需求」（小赢双目录、未逾期条件）时才引入，而非一开始就铺满抽象。`OverdueConditionEvaluator` 出现时，工厂基类已就位，零改动主流程即接入。

### 2. 配置 vs 代码
常变的业务规则（跳转、概率、模块列表）放配置；稳定的算法骨架（路径生成、继承链回溯）留代码。判断标准：换业务线是否要改？要改则进配置。

### 3. 可复现优先
`RandomService` 注入是项目最关键的基础设施之一。所有随机来源必须可控，否则无法 debug、无法回归、无法多进程独立种子。

### 4. 先观测后处理
Trace → 分析报告 → 调参；检测工具 → 去重工具。永远先让问题可见，再做清洗/优化，避免黑盒操作数据。

### 5. 命名即文档
`stop_prob` → `flexible_stop_prob`、`num_paths` → `num_dialogues`。当名字需要注释解释时，往往该改名而非加注释。

### 6. 防御性边界
防御性解析只放在系统边界（外部 Excel/txt 数据），内部代码信任数据格式。`parse_case_info` 提取金额数字是典型。

## 待决策的开放问题

- **1.0.0 兼容性冻结**：何时冻结配置结构？需确认 A/B 集、transition_rules 的 schema 是否还会变动。
- **去重工具集成**：去重是作为生成后自动步骤，还是保持独立工具让用户按需调用？目前倾向后者（灵活可控）。
- **条件解析复合逻辑**：`&`、`|` 运算符是否值得引入通用表达式引擎，还是继续按场景加专用 Evaluator？后者更简单但可能碎片化。
